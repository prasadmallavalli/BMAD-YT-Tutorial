# Story 2.5: Order Creation & Confirmation UI

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a user,
I want to create a new Order for a Customer, add OrderItems, choose an OrderType, and confirm it,
so that the customer's purchase is recorded and stock is reserved.

## Acceptance Criteria

1. **Given** the app is running, **When** I open "New Order", **Then** `OrderCreateForm` (`IOrderCreateView`) lets me pick a Customer, an OrderType (Standard/Rush), and add OrderItems (Product + quantity) via a line-item grid, through `OrderCreatePresenter` (one `IServiceScope` per action, AD-3).
2. **And Given** a filled-out order, **When** I click Confirm, **Then** the resolved `IOrderProcessor` asynchronously (NFR-1) validates stock via `IInventoryService.HasSufficientStockAsync` for every line item, computes the total (via `IPricingStrategy` + rush surcharge if applicable), persists the Order+OrderItems, decrements Inventory, and transitions status to `Confirmed` — all within one business operation — with the UI staying responsive throughout.
3. **And Given** a line item requests more stock than available, **When** I click Confirm, **Then** confirmation is rejected with a message identifying the insufficient-stock item(s); no Order is persisted and no Inventory is decremented (no partial decrement) — fulfilling FR-5.
4. **And Given** two near-simultaneous Confirm actions touch the same Product's Inventory, **When** the second commit detects a stale `RowVersion`, **Then** it fails with a `Result<T>` concurrency error surfaced to the user, not a silent overwrite — fulfilling NFR-2.

## Dev Notes

- **Orchestration lives inside `StandardOrderProcessor`/`RushOrderProcessor`, not a new `OrderService`.** This codebase has no `IOrderService`/`OrderService` — Story 2.3's `OrderProcessorFactory` and `IOrderProcessor` are the intended seam for exactly this orchestration, confirmed by Story 2.4's own Dev Notes ("Story 2.5 ... extends those same processor classes with `IUnitOfWork`/`IInventoryService`/`IOrderStatusService` orchestration"). Do not introduce a parallel `OrderService` class — that would create two competing owners of order-confirmation logic.
- **Order of operations is load-bearing, not stylistic**: stock-check (read-only) → persist Order+Items (1st save, gets `order.Id`) → decrement Inventory (2nd save, concurrency-guarded) → `TransitionTo` (3rd save + notify, inside `OrderStatusService`, already concurrency-guarded from Story 2.4). Three separate `SaveChangesAsync()` calls, not one wrapped transaction — this matches every prior story's one-save-per-mutation-group convention (no explicit `BeginTransactionAsync` exists anywhere in this codebase) and epics.md's "one async transaction" phrasing refers to one atomic **user action** (one Presenter-method invocation, AD-5's "business operation" definition), not a literal single SQL transaction.
- **Accepted edge case — a failed decrement or failed status transition leaves an `Order` row persisted with `Status = Unspecified` and (for a failed transition) Inventory already decremented.** This is a known, documented gap consistent with the PRD's "not a production system" scope boundary and this project's established pattern of accepting similar gaps (see `deferred-work.md`). Do not add compensating-transaction/rollback logic to close it — that is out of scope for this story.
- **`UnitPriceAtOrder` is a Presentation-side snapshot, not a BLL re-fetch.** The Form captures `ProductDto.UnitPrice` at "Add Item" click time (from the already-loaded product list) and stamps it onto the line item. The BLL processor trusts `CreateOrderRequest.Items[].UnitPriceAtOrder` exactly as given — it does **not** call `IProductService`/`IUnitOfWork.Products` to re-verify price. This matches `OrderItem.UnitPriceAtOrder`'s Domain doc comment ("a snapshot of `Product.UnitPrice` at add-time") from Story 2.1.
- **`OrderCreateForm` is a leaf form** (never opens another Form) — constructor takes `IServiceScopeFactory` only, matching `ProductDetailForm`'s Story 1.3 precedent, not `IServiceProvider`. `MainForm` is the one that resolves and launches it (already holds root `IServiceProvider` for exactly this purpose).
- **Existing processor tests will not compile without changes** — `StandardOrderProcessorTests.cs`/`RushOrderProcessorTests.cs` currently call the one-argument constructor directly; `OrderProcessorFactoryTests.cs`'s `BuildFactory()` resolves processors via a real (unmocked) `ServiceCollection` that will also need the three new dependencies registered. All three files are in scope for this story — see Task 5.
- **`HasSufficientStockAsync` failure and "not found" are folded into the same "insufficient stock" message.** `IInventoryService.HasSufficientStockAsync` returns `Result<bool>.Failure("Product not found")` for an unknown `ProductId` and `Result<bool>.Success(false)` for genuinely insufficient stock — both cases mean "this line item cannot be fulfilled," so the processor treats both as insufficient-stock for AC #3's message. Don't build a separate not-found code path.
- **No `IOrderRepository`/`IInventoryRepository`/DAL change needed.** `OrderRepository.AddAsync` (Story 2.1) and `InventoryRepository.GetByProductIdAsync` (Story 1.4) already provide everything this story's orchestration needs, both returning/accepting tracked entities from the shared per-operation `DbContext` (AD-2). Mutating `inventory.StockQuantity` directly on the entity from `GetByProductIdAsync` is picked up by EF's change tracker on the next `SaveChangesAsync()` — identical to how `OrderStatusService.TransitionTo` already mutates `order.Status` directly (Story 2.4).
- **Naming conventions (unchanged):** `IXxx` interfaces, `XxxPresenter`, `IXxxView`. `OrderLineItemRow` is a new Presentation-only view-model type — not a `Dto` (it never crosses into BLL) and not a `record` (no precedent for records in this codebase).
- **Data & formats:** `decimal` for all money fields (`UnitPriceAtOrder`, `LineTotal`), never `float`/`double` — consistent with the Consistency Conventions table.
- **Trust internal callers convention continues**: `OrderCreatePresenter.ConfirmAsync` does not re-validate `request` beyond what the Form's Confirm-click handler already assembled — matches the established "internal BLL entry point, not a system boundary" reasoning from Stories 2.2/2.4.

Added 3 regression tests per processor (duplicate-line-item aggregation, decrement-time insufficient-stock, decrement-time missing-row).
