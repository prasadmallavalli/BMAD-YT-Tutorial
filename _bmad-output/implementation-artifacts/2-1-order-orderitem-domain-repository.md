# Story 2.1: Order & OrderItem Domain, Repository

Status: done

## Story

As a developer,
I want Order and OrderItem entities and a repository wired through the Unit of Work,
so that Orders and their line items can be persisted.

## Acceptance Criteria

1. **Given** `OrderFlow.Domain`, **When** complete, **Then** an `Order` entity (`Id`, `CustomerId` FK, `OrderType`, `OrderStatus`, `RowVersion`, `IAuditable`) and `OrderItem` entity (`Id`, `OrderId` FK, `ProductId` FK, `Quantity`, `UnitPriceAtOrder` — a snapshot of `Product.UnitPrice` at add-time) exist with configs in `OrderFlow.DAL`, and a migration adds `Orders`/`OrderItems` tables with FKs to `Customers`/`Products`.
2. **And Given** `OrderFlow.DAL`, **When** implemented, **Then** `IOrderRepository`/`OrderRepository` is exposed only via `IUnitOfWork.Orders` (AD-9), supports persisting an Order with its OrderItems in a single `SaveChanges` call, and stamps `CreatedAt` only on `EntityState.Added` (AD-6).
3. **And Given** `OrderFlow.Domain`, **When** reviewed, **Then** `OrderStatus` includes at minimum a `Confirmed` value sufficient for order creation; the rest of the lifecycle is added in Epic 3.
4. **And Given** `OrderFlow.Tests`, **When** complete, **Then** `IOrderRepository` is covered by a test verifying an Order + OrderItems round-trip persists correctly.

## Dev Notes

- **`Order`'s status property is named `Status`, not `OrderStatus` — this overrides the AC parenthetical's literal wording.** The AC (and epics.md) list the field as "OrderStatus," but that's naming the *concept*, not dictating the C# property name. The Architecture Spine's own Structural Seed ERD is explicit on this point: `ORDER { OrderType OrderType; OrderStatus Status }` — note it does *not* write `OrderStatus OrderStatus`, unlike the `OrderType` line. That's a deliberate stutter-avoidance choice (`order.Status`, not `order.OrderStatus`, the same way you'd write `Customer.Name` not `Customer.CustomerName`). The ERD is the higher-authority document for this naming decision; follow it. Property type is still `OrderStatus` (the enum) — only the property name differs from the type name.
- **AC #2's `CreatedAt`-stamping requirement needs no new code.** `AppDbContext.StampAuditableEntries()` (built in Story 1.2) already stamps `CreatedAt` only on `EntityState.Added` for every `IAuditable` entity via `ChangeTracker.Entries<IAuditable>()` — this fires automatically the moment `Order`/`OrderItem` implement `IAuditable` (Tasks 2/3). Don't add repository- or entity-level stamping logic; it would be redundant.
- **This story is Domain + DAL only — no BLL types.** Unlike Story 1.2/1.4 (which each paired a domain/repository story with a `service` in the same story), Order's BLL surface is deliberately split across Story 2.2 (`IPricingStrategy`), Story 2.3 (`IOrderProcessor`/`OrderProcessorFactory`), and Story 2.4 (`IOrderStatusService`/`INotifier`) — no single `IOrderService` is even named across those stories. Do not invent an `OrderDto` or `IOrderService` here; this story's AC is exhaustive on that point (Domain entities, DAL repository, migration, DAL test only).
- **Cascade-insert pattern for `Order`+`OrderItems` mirrors Story 1.4's `Product`+`Inventory` exactly, just 1:many instead of 1:1:** populate `Order.OrderItems` before calling `AddAsync`, and EF Core inserts the whole graph (parent + children) in one `SaveChangesAsync`, wiring each `OrderItem.OrderId` FK automatically once `Order.Id` is generated. No two-step insert, no manually setting `OrderId` on the items beforehand.
- **`IAuditable` on `OrderItem` despite the AC parenthetical not naming it:** `Inventory` (Story 1.4) already established this precedent — its own AC bullet didn't list `IAuditable` either, but the actual `Inventory.cs` implements it, because AD-6 ("every Domain entity implements `IAuditable`") is a blanket architectural rule, not opt-in per AC wording. Apply the same reasoning here.
- **`RowVersion` only on `Order`, not `OrderItem`:** matches `Product`'s existing precedent — `Product` has no `RowVersion` even though AD-10 reads as a blanket rule; only entities the epics/story text explicitly calls out get one (`Inventory` in Story 1.4, `Order` here). Don't add one to `OrderItem`.
- **No navigation properties for the FK-only relationships** (`Order.CustomerId`, `OrderItem.ProductId`): `Customer` gets no `Orders` collection, `Product` gets no `OrderItems` collection. This mirrors `Inventory`'s existing unidirectional relationship with `Product` (no back-nav) — keep the entity graph minimal; nothing in this story's AC needs traversal from `Customer`/`Product` to their related Orders/OrderItems.
- **New DAL-testing infrastructure, scoped narrowly:** `deferred-work.md`'s Story 1.2 entry already flags "No DAL-level tests... against an in-memory/SQLite provider" as an accepted, deferred gap — but this story's own AC #4 explicitly requires a real repository round-trip test, which cannot be satisfied by the existing mocked-`IUnitOfWork` pattern every other `OrderFlow.Tests` file uses. Adding `Microsoft.EntityFrameworkCore.InMemory` and one round-trip test for `OrderRepository` satisfies AC #4 without resolving that broader deferred item — `CustomerRepository`/`ProductRepository`/`UnitOfWork`'s own DAL-level coverage (and the real `DbUpdateConcurrencyException` translation) remain deferred; don't retrofit tests for those here, out of scope.
- **Migration generation works without a live LocalDB connection** — same precedent as Story 1.2/1.4 (`AppDbContextFactory` is the design-time factory `dotnet-ef` uses; no actual SQL Server needs to be reachable to generate the migration file). `dotnet ef database update` (applying it to a real DB) remains the same `UNVERIFIED-ENVIRONMENT` gap already accepted since Story 1.1 (macOS dev machine, SQL Server LocalDB is Windows-only).
- **Quantity/pricing validation is out of scope here.** `OrderItem.Quantity`/`UnitPriceAtOrder` are plain persisted values with no validation logic in this story — stock-sufficiency checks (`IInventoryService.HasSufficientStock`, AD-13) and total calculation (`IPricingStrategy`, AD-11) are BLL concerns for later stories (2.2, 2.5), not this DAL-only one.
